# Accountable failed visit followup

`operations.field_visit_followup` is the sole writer of native accountability for an exact durable `FieldJobEvent(unable_to_complete)` or immutable rejected `CompletionReviewDecision`. Chat queue metadata is not an obligation. Intake directly projects every qualifying source without an obligation, including historical failures after later recovery, so missing responsibility stays visible without creating a fabricated owner or due time. A staff reviewer explicitly selects an active service team, an optional active native staff Person/member, and a timezone-aware due time. No appointment or revisit is inferred.

Migration680 adds one immutable source obligation, append-only numbered review snapshots and an owner-global UUID intent receipt. Initial disposition is triage. Further reviewed revisions explicitly select triage, revisit required, or no revisit with a required reason; no revisit is an accountable recorded disposition, not customer closure. The staff queue retains triage and revisit-required obligations; history includes no-revisit records. Original failed-source history never changes. Revisit required may remain pending approved issuance/linkage indefinitely and remains visible with due/team responsibility.

An optional replacement is an exact current approved migration679 decision, checked only through completion owner's typed `current_replacement_evidence`. The query binds the source WorkOrder and exact unable-event/assignment or rejected-submission/decision/review generation. Completion owns approval, scope equivalence, independence and engineering freshness. Same ticket, project, customer or job label never establishes replacement proof. A stored decision is historical review evidence; later approval revocation does not rewrite a followup revision. A new linkage review must pass current completion proof again.

Unified intake, queue, responsibility selector and workspace require both current dispatch READ and completion-review READ for the same native active staff principal. Unable-only creation requires dispatch ASSIGN; rejected-source commands additionally require completion READ. Replacement linkage requires completion WRITE as well. Every admission is freshly revalidated after lock waits. History remains readable without dispatch ASSIGN. The browser uses separate approved-replacement POST dependencies, CSRF, original revision and stable intent; conflicts preserve original inputs and require explicit reload before a new intent.

Lock order: owner-global intent advisory lock; optional completion evidence participant **before** followup locks (canonical Ticket linkage fence → Ticket → Project → ordered WorkOrders and completion graph); canonical WorkOrder linkage fence → WorkOrder → existing followup → selected service team → exact optional team member. No WorkOrder lock is held before entering completion's graph. Exact failed-source binding and author admissions are rechecked after WorkOrder wait; target native staff/Person/vendor facts and author admissions are refreshed after membership waits. The team/member locks remain through commit. This aligns with existing Ticket→WorkOrder and avoids a followup WorkOrder→completion Ticket inversion.

One owner executor atomically records obligation/head, snapshot, exact intent receipt, audit and typed `operations.field_visit_followup.recorded.v1` payload in a record-only custom event envelope. Record-only emission executes no handlers or callbacks. No scheduler, notifications, customer messages, work-order transitions, appointment booking, job issuance or customer closure occur. Exact receipt replay freshly authorizes before returning the original revision; conflicting fingerprint refuses. New intents require the exact current revision. Owner errors are final; database contention retries the whole transaction.

Migration680 is additive with no backfill, exact empty precreated-baseline adoption, database immutable revision/receipt/source guards and deferred contiguous-head checks. Downgrade refuses accountability evidence loss. Coordinator must run fresh and predecessor migrations and authored PostgreSQL concurrency/lineage tests on the dedicated test server. SQLite checks are fast owner/adapter evidence only.

Integration uses model import `app.models.field_visit_followup`, registry shard `provisioning_operations.visit_followup.SERVICES`, and browser router `app.web.admin.field_visit_followups.router`. The pending projection needs no new event handler or scheduler. A later source-detail shortcut can link to `/admin/dispatch/visit-followups`; it must not invent responsibility automatically.

The browser routes WorkOrder links by canonical `public_id` (`sub-*`), while typed commands retain native UUID identity. Direct pending-source review uses its own typed current readiness query, so a READ-only viewer sees history/evidence without an active assignment form. History pagination retains its mode. Approved linkage is a separate completion-WRITE GET: the completion-owned workspace selects only its exact current approved edge, `current_replacement_evidence` validates the original failed source, and a human job label/public ID is shown. No global UUID target picker is provided. POST carries the original decision ID and generation and revalidates both; conflict retains inputs with explicit reload.
