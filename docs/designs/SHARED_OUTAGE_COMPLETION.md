# Shared outage completion evidence

Migration 681 composes the existing Network restoration, actual infrastructure issuance, Field Completion acceptance/replacement and Support customer confirmation owners. It does not activate service, complete projects, create appointments, notify customers or rewrite failure/history.

`network.outage_completion_evidence` is the protected read and graph-lock resolver. Its actual executable dependencies are staff admission and WorkOrder linkage fences. Its authoritative inputs retain the original Network lifecycle, outage issuance, Support ticket, Subscription and WorkOrder record owners. The resolver never calls their lifecycle mutations. Named inbound Support/Field executor checks authorize flush-free participants; they are not outbound owner calls. Lifecycle and evidence use one pure immutable audience interpreter.

A complaint's selected service is proven by immutable `outage_complaint_correlation_receipts`, unique by incident and intent. Fingerprint, selected service, original reviewed revision, actor, reason and compact compatibility reference are native fields; generic idempotency storage is not an authority. Unknown history cannot silently become native proof. An explicit legacy review, using the existing staff correlation editor, records `reviewed_adoption`, current exact service/audience and reason, preserving the historical link. Resolved incidents can receive this review but cannot receive a new complaint link. Known native service proof cannot be rebound. The reviewed event is distinct from original link creation.

Support requires every complaint incident to be currently resolved with nonnull restoration time. For its exact selected service, every actual issuance whose immutable issued audience contains that service is required, including failed and unenrolled work. Each required original WorkOrder needs the existing current accepted completion basis, possibly through the same immutable reviewed replacement lineage. No title, task ticket hint or current topology determines membership. A zero matching set requires explicit `restored_without_issued_field_scope` review. This cannot waive an existing job.

A request pins immutable shared incident and work-scope children alongside existing original/effective completion bases. The staff page displays restoration and human-readable public WorkOrder links and posts the original exact scope selection. Request, confirmation and grace compare the same native snapshot. Reopen/re-resolve, new issuance/correlation, selected service rebinding, current audience revision changes and revoked/stale completion lineage require a fresh request. Customer dispute remains available when proof is stale. Any complaint link blocks direct closure, including unknown history.

Infrastructure replacement keeps `subscriber=None`. Both scopes require exact actual incident issuance, same canonical infrastructure ticket, target, classification, project/task and native provenance. The proof pins both immutable issued revisions and tokens. Replacement audience must contain every original issued service; growth is permitted, removal or same-count substitution is not. Existing full criterion coverage, failure, assignment, policy, reviewer independence, cycle/fan-in and accepted endpoint rules remain in the single 679 engine. Historical revocation copies the immutable proof without current restoration or issuance eligibility.

Lock preparation discovers roots before locks, then sorts all Incidents, all Ticket linkage fences and Tickets, distinct selected Subscriptions, Project/task roots, WorkOrders and heads. Complaint link identities are copied into immutable tuples before identity-map refresh; changed roots abort the whole transaction. No new Incident is acquired while holding a Ticket. Workqueue prepares before its target lock; unmatched-radio close batches prepare before the first Ticket write. Customer adapters pass their subscriber scope for fresh binding validation under the locked Ticket. Project completion callers prepare the typed required-WO graph before Project. Replacement graph expansion stays within exact enrollment scope and never locks unrelated projects through a shared ticket. Existing Ticket SLA paths lock Ticket before Subscription, consistent with this order.

SQL guards enforce native receipt lineage, exact shared mappings and complete basis, exact dual issuance replacement proof, and immutable issued revisions/audiences. No backfill invents service, actor or historical review authority. Migration adoption accepts only empty exact frozen native shapes; downgrade refuses immutable evidence loss. The coordinator alone runs migrated PostgreSQL concurrency and tamper acceptance on the dedicated test server.

Creation-only child guards use nullable server-owned `creation_outer_xid` (`pg_catalog.xid8`) on scope revisions, incident-ticket links, support requests and replacement decisions. BEFORE INSERT always stamps `pg_current_xact_id()` and BEFORE UPDATE refuses marker changes; callers cannot supply authority. The complete outer transaction identity remains exact through nested, released and sibling savepoints, including classifier reconciliation and connection-bound owner coordinators. Historical parents retain NULL: no backfill or DEFAULT implies current creation. Child insertion compares full xid8 equality, avoiding truncated xmin, subtransaction identifiers and epoch ambiguity. Earlier frozen adoption gates accept only their specifically named nullable xid8 extension without DEFAULT, identity or generated expression; all other shape checks remain exact.
