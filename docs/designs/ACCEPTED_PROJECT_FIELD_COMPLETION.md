# Accepted project and task field completion

Explicit physical enrollment registers an immutable project-owned requirement in the same field-completion transaction. Migration682 backfills only existing explicit enrollment/project/task pairs. Historical terminal scopes remain terminal. New enrollments on terminal scopes refuse. Issued but unenrolled legacy scope keeps its existing lifecycle policy.

Projects owns requirement scope and lifecycle writes. Field completion owns the explicit `ApplyAcceptedProjectCompletion` command and shared accepted-evidence interpretation. Projects does not depend on completion review or read approval tables. The protected registration and completion participants require the existing active `operations.field_completion` executor and flush only.

Project scope covers all registered project requirements. Task scope covers all registered direct and descendant task requirements, including historical inactive descendants. Project-level requirements do not belong to task completion. Marked tasks, ancestors and project roots cannot be archived or reparented to escape the registry. Current project customer binding must equal the enrollment-time snapshot.

The staff action requires fresh `project:update` or `project:task:write` admission before and after waits, exact project/task revisions, exact requirement token, mandatory reason and UUID intent. This grants no completion review approval. Staff choose the existing project/task and see labeled field visits and owner-produced readiness. API and admin adapters submit the same typed action. Stale form values and intent are preserved; an explicit reload obtains a new preview.

The outer field-completion command calls the common scoped acceptance collector for every exact required WorkOrder and enrollment. That kernel checks current effective acceptance, all ordered reviewed replacement edges, canonical assignment generation, policy/criteria and engineering/incident proof. A rejected original may be satisfied by a reviewed replacement only after the replacement's independent acceptance. Every original requirement remains in the frozen basis. No local acceptance policy or cached accepted flag exists in projects or presentation.

Lock order starts with one globally ordered network completion graph preparation (Incident, canonical linkage fences, Tickets), then sorted observed Ticket/WorkOrder linkage fences and Tickets, then Project and task rows. Requirements are reread under Project; changed required identities abort for refresh instead of acquiring missing linkage fences late. Shared proof locks follow the same roots. Raw task SQL uses a nonblocking parent Project lock and fails for retry when another transaction owns it; it never waits while reversing Project→Task order.

One owner executor atomically records immutable application, original/effective accepted bases, contiguous replacement lineage, UUID intent receipt, canonical project/task transition output and audit. The protected project participant requires the application created in this transaction and exact full registry coverage. SQL guards compare its server-stamped `creation_outer_xid` (`xid8`) with `pg_current_xact_id()`, preserving the full outer transaction identity across nested, released and sibling savepoints. PostgreSQL stamps the value unconditionally before insert and refuses later mutation; callers cannot choose it. There is no DDL default or historical backfill, and a NULL historical marker never authorizes new children or completion. A physical commit ends the creation boundary; later transactions cannot append bases, lineage or receipts to that application. Exact receipt replay freshly revalidates permission, scope and the complete accepted basis before returning the stored outcome. Later review revocation invalidates replay without rewriting historical terminal status.

Migration682 freezes five-table adoption shape, refuses nonempty or incompatible adoption, and adds SQL immutability, exact requirement pairing, effective accepted-head pairing, ordered lineage, full coverage, receipt/intent binding, and generic status/archival guards. These guards complement owner proof; authoritative migration/race evidence requires the real PostgreSQL chain on the dedicated test server. SQLite unit checks are not schema or concurrency acceptance.

The explicit action preserves existing task dependency and child completion checks. It emits existing canonical project/task transition output once. It does not commission, provision, activate, close customer tickets, restore shared infrastructure, bill or release payment. Engineering review of existing evidence on held origins remains governed by the canonical completion participant; new issuance policy remains separate.
